Testing your code

Up to now, we have checked our functions by calling them and looking at what is printed: println(convert_temperature(100, unit="C")) # Outputs: 212.0. This is already a test, but a fragile one: you have to read the output, compare it with the expected value, and redo it by hand every time the code changes. In this page, you will learn to write automated tests: small pieces of code that check that your functions behave as expected, and that you can run again in one command after each modification.

Tests are useful to:

  • find bugs early, while the code is still fresh in your mind;
  • modify code without fear: if you break something, a test will tell you;
  • document how a function is supposed to be used, with concrete examples.

The Test standard library

Julia ships with the Test standard library: there is nothing to install, just load it.

using Test

The @test macro

The macro @test evaluates an expression that must return true or false. If the result is true, the test passes.

@test 1 + 1 == 2
Test Passed

If the result is false, the test fails and Julia reports both sides of the comparison, which helps to understand what went wrong.

@test 1 + 1 == 3
Test Failed at In[5]:2
  Expression: 1 + 1 == 3
   Evaluated: 2 == 3

Comparing floating-point numbers

Floating-point numbers are stored with a finite precision (see the page on types), so exact comparisons can fail even when the mathematics is correct:

@test 0.1 + 0.2 == 0.3
Test Failed at In[6]:2
  Expression: 0.1 + 0.2 == 0.3
   Evaluated: 0.30000000000000004 == 0.3

To compare floating-point numbers, use the approximate comparison ≈ (type \approx then Tab), which is the function isapprox. You can control the tolerance with the keyword arguments atol (absolute tolerance) and rtol (relative tolerance).

@test 0.1 + 0.2 ≈ 0.3
@test π ≈ 3.14 atol = 1e-2
Test Passed
Warning

By default, ≈ uses only a relative tolerance. Therefore x ≈ 0 is true only if x == 0! When the expected value is zero, always give an absolute tolerance: @test x ≈ 0 atol = 1e-10.

Testing errors with @test_throws

A function must also behave correctly when it receives invalid inputs. Recall the function convert_temperature from the page Structure your code, which throws an ArgumentError for an unknown unit:

function convert_temperature(value; unit)
    if unit == "C"
        return value * 9/5 + 32
    elseif unit == "F"
        return (value - 32) * 5/9
    else
        throw(ArgumentError("Unit must be 'C' or 'F'"))
    end
end

The macro @test_throws checks that an expression throws an exception of the given type:

@test_throws ArgumentError convert_temperature(10, unit="K")
Test Passed
      Thrown: ArgumentError

Grouping tests with @testset

Tests are grouped into test sets. A test set runs all its tests, even if some of them fail, and prints a summary at the end. Test sets can be nested.

@testset "convert_temperature" begin
    @testset "Celsius to Fahrenheit" begin
        @test convert_temperature(100, unit="C") ≈ 212
        @test convert_temperature(0, unit="C") ≈ 32
    end
    @testset "Fahrenheit to Celsius" begin
        @test convert_temperature(32, unit="F") ≈ 0 atol = 1e-12
    end
    @testset "invalid unit" begin
        @test_throws ArgumentError convert_temperature(10, unit="K")
    end
end;

Other useful macros

Macro Usage
@test ex ex must return true.
@test a ≈ b atol=... approximate comparison.
@test_throws T ex ex must throw an exception of type T.
@testset "name" begin ... end groups tests and prints a summary.
@test_broken ex documents a known bug: the test is expected to fail.
@inferred f(x) checks that the return type of f(x) is inferred by the compiler (see type stability).

What should I test? The contract of a function

Before writing tests, you need to know precisely what the function is supposed to do. This specification is called the contract of the function, and the right place to write it is the docstring, just above the function. A contract states:

  • the preconditions: what the inputs must satisfy;
  • the postconditions: what the function returns (or modifies) when the preconditions hold;
  • what happens when the preconditions are not satisfied (typically, which error is thrown).
"""
    my_mean(v)

Return the arithmetic mean of the vector `v`.

- Precondition: `v` is a non-empty vector of real numbers.
- Postcondition: returns `sum(v) / length(v)`; `v` is not modified.
- Throws an `ArgumentError` if `v` is empty.
"""

Once the contract is written, a good test suite covers:

  1. typical cases: a few “normal” inputs for which you know the answer (computed by hand);
  2. edge cases: the smallest inputs (empty vector, one element), the values exactly at a boundary (if a condition reads x >= 10, test 9, 10 and 11), zeros, negative numbers…;
  3. invalid inputs: one @test_throws per error described in the contract;
  4. properties: relations that must always hold, even if you do not know the exact result (a converted temperature converted back gives the initial value, the output of a sort is sorted, the input is not modified…).
Important

A test that is never red is useless. When you write a test, check that it is able to fail: temporarily break the code and verify that the test detects it.

Organising tests in a package

In a notebook or in the REPL, you can write tests anywhere. In a real project, the code lives in a package and the tests in a separate folder, so that anyone can run them with a single command. Creating a package takes one line in the package mode of the REPL (see Developer set up):

] generate MyStats

Then add the folder test with a file runtests.jl, so that your project looks like this:

MyStats/
├── Project.toml
├── src/
│   └── MyStats.jl      # the code: module MyStats ... end
└── test/
    └── runtests.jl     # the tests

The file src/MyStats.jl contains the module (see Modules):

module MyStats

export my_mean

"""
    my_mean(v)

Return the arithmetic mean of the non-empty vector `v`.
Throw an `ArgumentError` if `v` is empty.
"""
function my_mean(v)
    if isempty(v)
        throw(ArgumentError("v must be non-empty"))
    end
    return sum(v) / length(v)
end

end

The file test/runtests.jl loads the package and runs the tests:

using MyStats
using Test

@testset "MyStats" begin
    @test my_mean([1, 2, 3]) == 2
    @test my_mean([1.0, 2.0]) ≈ 1.5
end

Finally, declare Test as a dependency used only for testing by adding these lines at the end of Project.toml:

[extras]
Test = "8dfed614-e22c-5e08-85e1-65c5234f0b40"

[targets]
test = ["Test"]

From the folder MyStats, start Julia, activate the package and run its tests:

Code coverage

All tests pass… but is all the code tested? The code coverage measures which lines of your code have been executed by the tests. The package LocalCoverage.jl runs the tests and prints a report. Install it once in your global environment (not in the package):

] activate
] add LocalCoverage

Then, from the folder containing MyStats:

using LocalCoverage
cov = generate_coverage("MyStats")               # runs the tests with coverage
show(IOContext(stdout, :print_gaps => true), cov) # also print the missed lines
┌────────────────┬───────┬─────┬──────┬─────┬──────┐
│ Filename       │ Lines │ Hit │ Miss │   % │ Gaps │
├────────────────┼───────┼─────┼──────┼─────┼──────┤
│ src/MyStats.jl │     4 │   3 │    1 │ 75% │ 13   │
├────────────────┼───────┼─────┼──────┼─────┼──────┤
│ TOTAL          │     4 │   3 │    1 │ 75% │      │
└────────────────┴───────┴─────┴──────┴─────┴──────┘

Line 13, throw(ArgumentError(...)), is never executed: we forgot to test the empty vector. Adding @test_throws ArgumentError my_mean(Int[]) to the tests brings the coverage to 100%.

Coverage is a tool, not a goal

A line that is executed is not necessarily verified: my_mean([1, 2, 3]) executes every line of a wrong implementation as well. Moreover, coverage cannot see code that is missing (a forgotten if). A coverage of 100% does not mean that the code is correct; a low coverage, however, tells you for sure that some parts of the code are not tested.

Note

In the package directory, ] test can also be run from a terminal with julia --project -e 'using Pkg; Pkg.test()'. This is what continuous integration services (for instance GitHub Actions) do after each modification of the code.

Exercise 3: The tests are red, fix the code

The bisection method finds a root of a continuous function f on an interval [a, b] such that f(a) and f(b) have opposite signs, by halving the interval repeatedly. Here is a first implementation, with its contract:

"""
    bisection(f, a, b; tol=1e-12, max_iter=100)

Find a root of the continuous function `f` in the interval `[a, b]`.

- Preconditions: `a < b` and `f(a) * f(b) ≤ 0`.
- Postcondition: returns a tuple `(x, iter)` where `x` is an approximation of a root
  of `f` in `[a, b]` and `iter` is the number of iterations. If `f(a) == 0` (resp.
  `f(b) == 0`), then `x == a` (resp. `x == b`).
- Throws an `ArgumentError` if a precondition is not satisfied.
"""
function bisection(f, a, b; tol=1e-12, max_iter=100)
    if f(a) * f(b) > 0
        error("The function must have opposite signs at the endpoints a and b.")
    end
    mid = (a + b) / 2
    iter_count = 0
    while (b - a) / 2 > tol && iter_count < max_iter
        iter_count += 1
        mid = (a + b) / 2
        if abs(f(mid)) ≤ tol
            return mid, iter_count
        elseif f(a) * f(mid) < 0
            b = mid
        else
            a = mid
        end
    end
    return mid, iter_count
end

Here are the tests of this function:

@testset "bisection" begin

end

  2. Fix the function until all the tests pass. You must not modify the tests!
  3. Bonus: the function f is evaluated several times at the same point. Modify the code so that each iteration evaluates f only once, and check that the tests still pass. This is the main interest of tests: you can improve the code safely.
Hint for Exercise 3

Four tests fail. Look at what happens in the loop when f(a) == 0: what is the value of f(a) * f(mid)? Also, which type of exception does the function error throw?

Correction of Exercise 3

The failing tests are:

  • bisection(x -> x, 0.0, 1.0): since f(a) == 0, the product f(a) * f(mid) is always 0, so the code always executes a = mid and moves away from the root. It returns a value close to 1 instead of 0.
  • bisection(x -> x - 1, 0.0, 1.0): the method converges to 1 but never returns exactly b.
  • bisection(x -> x^2 + 1, 0.0, 1.0): error(...) throws an ErrorException, not an ArgumentError.
  • bisection(x -> x, 1.0, -1.0): the condition a < b is never checked. The loop is not executed and the function returns silently.

A corrected version, which also evaluates f only once per iteration:

function bisection(f, a, b; tol=1e-12, max_iter=100)
    a < b || throw(ArgumentError("a must be smaller than b"))
    fa, fb = f(a), f(b)
    fa == 0 && return a, 0
    fb == 0 && return b, 0
    fa * fb < 0 || throw(ArgumentError("f(a) and f(b) must have opposite signs"))
    mid = (a + b) / 2
    iter_count = 0
    while (b - a) / 2 > tol && iter_count < max_iter
        iter_count += 1
        mid = (a + b) / 2
        fmid = f(mid)
        if abs(fmid) ≤ tol
            return mid, iter_count
        elseif fa * fmid < 0
            b = mid
        else
            a, fa = mid, fmid
        end
    end
    return mid, iter_count
end

Exercise 4: Some tests are missing

The following function gives the honours associated with an exam grade:

"""
    honours(grade)

Return the honours associated with a `grade`.

- Precondition: `0 ≤ grade ≤ 20`.
- Postcondition: returns
    - `"Excellent"` if `grade ≥ 16`,
    - `"Very good"` if `14 ≤ grade < 16`,
    - `"Good"` if `12 ≤ grade < 14`,
    - `"Pass"` if `10 ≤ grade < 12`,
    - `"Fail"` if `grade < 10`.
- Throws a `DomainError` if the precondition is not satisfied.
"""
function honours(grade::Real)
    if grade < 0
        throw(DomainError(grade, "grade must be in [0, 20]"))
    end
    if grade >= 16
        return "Excellent"
    elseif grade > 14
        return "Very good"
    elseif grade >= 12
        return "Good"
    elseif grade >= 10
        return "Pass"
    else
        return "Fail"
    end
end

    end
end;

To go further: what does the coverage say?

Create a package Grades (see Organising tests in a package) containing the initial (buggy) function honours, with the initial tests of your colleague in test/runtests.jl. Run the coverage with LocalCoverage.

  1. Which lines are not covered? Are the bugs on these lines?
  2. One of the two bugs cannot be detected by the coverage, even in theory. Which one, and why?

Answer. The lines returning "Very good", "Good" and throwing the DomainError are never executed: the coverage invites you to write tests for them. Testing "Very good" at the boundary 14 reveals the bug grade > 14. However, the missing condition grade > 20 is absent from the code: there is no line to cover. Only the contract tells us that this case must be tested. This is why tests are written from the contract, and coverage is only used to check that no part of the code has been forgotten.
